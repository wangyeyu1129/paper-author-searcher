# 基准测试：链接验证可以离线重放（2026-10-29）

## 问题

原文覆盖率的对比一直受网络噪声影响：
- 元数据 GET 请求有缓存，但链接验证（probe）每次都实时联网；
- 两次运行只要隔几个小时，网站的拦截和故障就不同。例如 Europe PMC 的 403 一次是 122 个，另一次是 1079 个。

所以对照组和新代码组之间的差异，一部分其实是网络造成的。

## 改动

HTTP 缓存现在也记录：
- **链接验证**：包括重定向的每一跳、状态码、响应头（只保留 `Content-Type`、`Content-Length`、`Content-Range`、`Retry-After`，不存 Cookie）和读到的前缀（压缩存储）；
- **JSON POST**：Semantic Scholar 的批量查询，key 不含 API key；
- **失败结果**：GET、POST 和链接验证的失败都会记录。

三种模式：
- **record（录制）**：使用已存的成功结果；遇到已存的失败会重新请求，因为失败可能只是临时的；
- **replay（重放）**：成功和失败都按录制时的结果返回，不联网；没有记录的请求直接报 `cache_miss`；
- **refresh（刷新）**：全部重新请求。

重放时，从缓存返回的回答：
- 不排队等待；
- 不受主机冷却期限制，也不会触发新的冷却期。

所以重放结果不受运行快慢影响，每个链接都得到录制时的结论。

调度器自己产生的推迟（`source_deferred`）、缓存缺失和离线拒绝不会被记录，因为它们反映的是这次运行的状态，不是网站的回答。

## 验证

5 人（Hie、Jia Liu、Kallini、Sindy Tang、Wolf）：先录制一次，再完全离线重放两次。

| | 录制 | 重放 1 | 重放 2 |
|---|---:|---:|---:|
| 用时 | 585 秒 | 347 秒 | 346 秒 |
| 有通过验证链接的论文 | 30 / 4 / 9 / 11 / 25 | 相同 | 相同 |
| GET 缓存缺失 | | 0 | 0 |

逐个比对 322 个链接：
- **两次重放之间差异为 0**，状态码、最终地址也完全相同。
- **录制与重放之间**，结论（身份、验证状态）全部相同。有 6 处诊断字段不同：录制时 Europe PMC 的 500 被调度器推迟后没有记录状态码，重放时同一链接直接返回已存的结果。

重放时仍有一部分链接验证没有记录（每人 53–67 个）。它们在录制时被冷却期推迟，从未真正请求过，所以重放时一律记为缺失。结论同样确定，不会因运行而变化。

## 用法

先用 `record` 跑一次控制组代码，再用 `replay` 分别跑控制组和新代码组。两者的差异只来自代码。

重放时仍会按 Semantic Scholar、arXiv 的请求间隔等待（这层节流在缓存之上），所以重放不是瞬间完成的。
